把 JWT 双令牌重写
了一遍才懂

2026-09-11约 3200 字 · 读完 11 分钟1.2k 次翻看

登录鉴权这块，我之前一直是"能跑就行"。直到答辩预演被问"Access Token 过期了怎么办"，才认真把双令牌方案完整写了一遍。这篇按我的理解顺序记录。

为什么要两个 Token

单个 Token 的矛盾在于：有效期长则被盗风险高，有效期短则用户频繁重新登录。双令牌把"身份凭证"和"续期凭证"分开——

  • Access Token：有效期 2 小时，随每个请求携带，服务端无状态校验；
  • Refresh Token：有效期 7 天，只在续期接口出现，存 Redis 可随时吊销。
一句话：Access 管"现在能不能进"，Refresh 管"还能不能续"。分工不同，安全边界就清晰了。

续期流程

前端在 Axios 响应拦截器里捕获 401，静默调用 /api/portal/auth/refresh，拿到新 Access 后重放原请求。期间的其他请求挂起，避免并发刷新导致多次续期。

退出登录怎么作废 Token

JWT 本身无法主动作废，所以用 Redis 黑名单补位：退出时把 Access Token 的 jti 写入黑名单，TTL 设为该 Token 的剩余有效期——到期后黑名单条目自动消失，不占内存。

// JwtAuthenticationFilter 中每次请求先查黑名单
if (redisTemplate.hasKey(BLACKLIST + jti)) {
    throw new BusinessException(401, "登录已失效");
}

小结

重写一遍的最大收获：安全方案不是"加一个中间件"就完事，而是一整套签发 → 携带 → 校验 → 续期 → 作废的生命周期设计。生命周期想清楚了，代码只是翻译。
