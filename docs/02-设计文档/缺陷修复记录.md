## 一、专项扫描结果

### 1.1 扫描方法

对 `blog-web/src` 下 **47 个 .vue 单文件组件**做两轮静态扫描：

| 轮次 | 检查内容 | 判定依据 |
|---|---|---|
| 第一轮 | 可交互标签是否缺失事件 | `<button>` / `<el-button>` / `<a>` / 带 `btn`、`cursor-pointer`、`role=button` 的伪按钮，其开标签（跨行属性聚合）中既无 `@click`/`@keyup` 等事件，也无 `:to`/`href` 导航，且未 `disabled` |
| 第二轮 | 事件指向的处理函数是否存在 | 提取 `@click="fn"` 的标识符，与 script 中的 `const`/`function`/`import`/方法简写定义集合比对 |
| 补充 | 空函数体与未实现标记 | 匹配 `= () => {}`、`function f() {}` 空体，及 `TODO`/`FIXME`/`待实现` 注释 |

### 1.2 扫描结论

**共发现 0 处真实的「按钮无事件绑定」缺陷。** 初筛报出的 3 处均为误报，逐项核实如下：

| 序号 | 位置 | 初筛判定 | 核实结论 |
|---|---|---|---|
| 1 | `views/error/NotFoundView.vue` L11 | `<button>` 无事件 | **误报**。该元素为循环飘落的装饰卡片，带 `aria-hidden="true"` 与 `tabindex="-1"`，属有意为之的非交互元素；同区域第一个按钮 `@click="goHome"` 正常 |
| 2 | `views/admin/ArticleEditView.vue` L74 | `<span class="btn">` 无事件 | **误报**。该 `<span>` 是 `v-for="btn in toolbar"` 循环体内的图标/文字载体，事件 `@click="btn.action()"` 绑定在父级 `<button>` 上 |
| 3 | `views/user/LoginView.vue` L91 | 「忘记密码？」按钮无事件 | **误报（见下方说明）**。读取时拿到的是文件**旧内容快照**；实际文件中该按钮已有 `@click="openReset"`，跳转至独立页面 `/forgot` |

### 1.3 补充扫描

- 空函数体（点了没反应）：**0 处**
- `TODO` / `FIXME` / 待实现标记：**0 处**
- `@click` 指向未定义函数：**0 处**（9 条初筛告警全部为模板内局部变量，如 `v-for` 的 `btn`、解构出的 `prev`/`toggle`/`next`）

## 二、误判复盘（重要）

### 2.1 发生了什么

在扫描 LoginView 时，基于**过期快照**判定「忘记密码？」按钮是死按钮，并已动手实施修复：

1. 在 `api/auth.ts` 追加 `findAccount` / `sendResetCode` / `resetPassword` 封装与 `ResetChannel` / `FindAccountResult` 类型
2. 在 `LoginView.vue` 加入三步找回密码弹层（约 130 行 template + 约 110 行 script + 过渡样式）

`vue-tsc` 随即报出 `TS2393 Duplicate function implementation`，暴露真实情况：

| 项目已有的实现 | 位置 |
|---|---|
| 独立的找回密码页面（576 行，含步骤指示器、三步表单） | `views/user/ForgotPasswordView.vue` |
| 路由声明 | `router/index.ts` L106 `path: 'forgot'`，`meta.title = '找回密码'` |
| 跳转逻辑 | `LoginView.vue` 中 `openReset()` → `router.push({ path: '/forgot', query })` |
| 接口封装 | `api/auth.ts` L72–112 三个函数 + 两个接口类型 |
| 后端接口 | `/auth/find-account`、`/auth/send-code`、`/auth/reset-password` |

即**功能早已完整实现**，我构建的弹层是没有必要的重复造轮子。

## 三、经验规律（写入后续约定）

| 编号 | 规则 |
|---|---|
| R1 | 修改文件前**必须重新读取最新内容**，不得基于对话早期的读取结果动手改代码 |
| R2 | 静态扫描报出「函数/绑定不存在」时，**先怀疑读到的是旧快照或局部作用域变量**，再考虑是真缺陷 |

### 6.6 本轮变更：IP 归属地改用 ip2region 离线库（2026-10-05）

**问题**：IP 归属地原走两条互不相干的实现，且**两条都不准**。

| 调用方 | 原实现 | 实际行为 |
|---|---|---|
| `t_visit_log.province`（访问埋点） | `ProvinceResolver` 调 `whois.pconline.com.cn` 免费接口，GBK 解码 + `ConcurrentHashMap` 缓存 | 依赖无 SLA 的第三方接口；且 `computeIfAbsent(ip, this::queryRemote)` 把**解析失败的结果也一并缓存**——接口抖动一次，该 IP 之后永远返回「未知」；缓存仅在单实例内存，重启即失效 |
| `t_message.ip_location`（留言属地） | `IpUtils.getLocation(ip)` | 只识别回环/内网，**公网 IP 一律返回「未知」**——即留言属地功能对线上访客实际从未生效 |

**另发现一处死代码**：`ProvinceResolver.isLocal()` 第 74 行已用 `ip.startsWith("172.")` 将整个 `172.*` 判为内网并 `return true`，紧随其后第 77–85 行「仅 172.16–31 为私网、其余为公网」的判断**永远不可达**，导致公网 `172.x` 段被误标为「本地」。（同类判断在 `IpUtils.getLocation()` 中写法正确，仅此一处写错。）

**处置**：统一改为 **ip2region 离线 xdb** 解析，两条链路共用一个组件。

| 层 | 变更 |
|---|---|
| 依赖 | `pom.xml` 新增 `org.lionsoul:ip2region:3.3.7` |
| 数据文件 | `blog-backend/src/main/resources/ip2region/ip2region_v4.xdb`（11,122,036 字节，随包内置）；仅引入 IPv4 库，未引入 37MB 的 IPv6 库 |
| `ProvinceResolver` | 重写：构造时用 `Searcher.loadContentFromInputStream(getResourceAsStream)` 载入 xdb 到内存（此写法在 IDE 运行与 fat jar 运行下均可用，直接传文件路径在 fat jar 中会失败），`newWithBuffer(Version.IPv4, …)` 做纯内存二分查找；移除 `HttpClient`、GBK 解码与内存缓存 |
| 解析规则 | v3 数据格式为 `国家\|省份\|城市\|ISP\|国家码`，取索引 1；回环/内网与 xdb 的 `Reserved` 段统一记 **「本地」**，中国 IP 取省份并去掉「省/市/自治区」后缀，境外 IP 记国家名，IPv6 与解析异常记 **「未知」**；xdb 缺失或损坏时仅告警不阻断启动 |
| `isLocal()` | 修掉 `172.` 死代码：改为「`10.` / `192.168.` / `169.254.` 直接判私网，`172.` 需第二段在 16–31 之间才算私网」，异常分支返回值由 `true` 改为 `false` |
| 留言链路 | `MessageService` 改为注入 `ProvinceResolver`，`message.setIpLocation(provinceResolver.resolve(clientIp))`；`IpUtils.getLocation()` 随之删除（已无调用方） |

**真机验证**（新 jar 启动，xdb 载入日志 `11122036 bytes`）：

| 输入 IP | 解析结果 | 说明 |
|---|---|---|
| 183.14.30.1 / 220.181.38.148 / 114.114.114.114 / 223.5.5.5 | 广东 / 北京 / 江苏 / 浙江 | 埋点与留言两条链路均正确落库 |
| 127.0.0.1 / 192.168.1.9 / 172.20.1.1 | 本地 | 回环与 RFC1918 私网 |
| **172.32.1.1** | **United States** | **修复生效的直接证据**——修复前会被死代码误判为「本地」 |
| 2400:3200::1（IPv6） | 未知 | 接口返回 200，不抛异常 |

**新增规律**：

| 编号 | 规则 |
|---|---|
| R16 | 「第三方免费接口 + 结果缓存」的组合必须区分**成功缓存**与**失败缓存**：`computeIfAbsent` 会把异常返回值一并固化，接口一次抖动即造成该 key 永久性错误。若必须缓存，只缓存成功结果；离线数据文件（如 xdb）是更稳的选择——无网络、无 SLA、无缓存失效语义 |
| R17 | 同一职责出现**两套实现**（`ProvinceResolver` 与 `IpUtils.getLocation`）时，通常意味着两条链路各自演化、无人对齐——审计 IP/时间/脱敏这类横切功能要直接搜「有没有第二个同类方法」，而不是只看主链路 |
| R18 | 长 `if` 链里的**前缀匹配早返回**极易压死后续精细判断：写「先宽后窄」的 IP/路径/枚举判定时，必须回头确认窄条件是否可达（本轮 `172.` 段即为此类） |

### 6.7 本轮变更：实现双 Token 会话机制（2026-10-07）

**变更性质**：不是缺陷修复，而是**补齐审计指出的能力缺口**——原设计只在 `request.ts` 里清理 `refresh_token`，
但后端从未实现 refresh 与登出撤销，属「死代码」，token 签发后 72h 内不可撤销。

| 层 | 变更 |
|---|---|
| 配置 | `application.yml` 的 `jwt.expire-hours: 72` 拆为 `jwt.access-hours: 2` + `jwt.refresh-days: 7` |
| JWT | `util/JwtUtil.java` 重写：`issueAccess(userId, role)` / `issueRefresh(userId, jti)`；两类 token 带 `claim("type")` 防混用；`parseAccess` / `parseRefresh` 分别校验 |
| 撤销 | 新增 `service/TokenService.java`：Redis `blog:auth:refresh:{jti}` → `userId`，TTL 7 天，**删除即撤销**；未登记 jti 一律拒绝 |
| 服务 | `UserService` 新增 `refresh()`（parseRefresh → isRegistered → 回库查用户 → revoke 旧 jti → 发新对）与 `logout()`；`buildVO` 生成 `jti` 并登记 |
| 接口 | `AuthController` 新增 `POST /auth/refresh`、`POST /auth/logout`；新增 DTO `RefreshTokenDTO` / `LogoutDTO`；`LoginVO` 增 `refreshToken` |
| 拦截器 | `AuthInterceptor` 改用 `parseAccess`——**refresh 不能当请求凭证** |
| 前端 | `request.ts` 重写：401 拦截 → 单飞刷新（模块级 Promise）→ 重放原请求（`_retried` 防循环），失败跳登录；`auth.ts` 增 `refreshAuth` / `logoutApi`；`stores/user.ts` 登出改调接口；登录 / 注册页保存双 token |
| 数据库 | **无表变更**——撤销状态存 Redis |
