## 上传体积口径统一为 1028MB（用户指令「都改成1028MB」）

上一轮发现音频上限有 3 套数字打架，用户裁定统一为 **1028MB**（不改成 25MB/1024MB）。

| 位置 | 改前 | 改后 |
|---|---|---|
| `application.yml` L12 注释 | 「音频（mp3/flac）**≤2056MB**」 | 「单文件上限：图片 ≤5MB、头像 ≤2MB、音频 ≤1028MB」+ 三行说明 `max-request-size` 的性质 |
| `application.yml` L13-16 | `max-file-size: 1028MB` / `max-request-size: 2056MB` | **不变**（值本就正确） |
| `StorageService.MAX_AUDIO_SIZE` + 错误文案 | `1028L*1024*1024` / 「不能超过 1028MB」 | **不变**（本就 1028MB） |
| `MusicManageView.vue` L57 前端提示 | 「mp3 / flac，**≤25MB**」 | 「mp3 / flac，**≤1028MB**」 |
| 测试用例 K06 | 「上传音频（≤1028MB）→ 成功」（类型：正常） | 「恰好 1028MB 通过 / 超出 1MB 拦截」（类型：**边界**） |
| 测试用例 编写依据 | 未标容器层出处 | 补 `application.yml` L11–15 与 `max-request-size` 非音频上限的说明 |

**关键判断（要记住的理由）**：`max-request-size` **没有**跟着改成 1028MB，因为它统计的是整个 multipart 请求体
（含 boundary 与表单开销），必须**大于**单文件上限；两者都设 1028MB 时，一个恰好 1028MB 的文件会在容器层被拒，
使 `StorageService` 里的 1028MB 校验永远走不到（变成死代码）。

## blog-web dev / preview 视觉不一致（用户指令：统一，保留 preview 的两侧留白）

### 根因（已定位并修复）
`blog-web/src/styles/tokens.css` 的 `--shell-max` 被改坏：

| 环境 | 产物 | 值 | 效果 |
|---|---|---|---|
| preview(4173) | `dist/`（**9/23 17:26 构建**） | `clamp(1120px, 88vw, 1560px)` | 1920 屏版心 1560，两侧各留 ~180px |
| dev(5173) | 当前 `src/` | `clamp(100%, 88vw, 1560px)` | 下限 100% ⇒ 恒 ≥ 视口宽 ⇒ `max-width` 永不生效，塌成全宽 |

- **原理**：`clamp(100%, 88vw, 1560px)` = `max(100%, min(88vw,1560px))`，大屏下 `min` 得 1560、
  再与 `100%(=视口)` 取大 → 等于视口宽。**clamp 的下限必须是绝对长度，不能是百分比**，
  否则 `max-width` 被架空。这是全站唯一一处实质差异。
- 已改回 `clamp(1120px, 88vw, 1560px)`，并把「下限不可写 100%」的原因写进注释，
  同步修正 `base.css` 里 `.shell` 上方那句已失效的旧注释。
- 窄屏安全性：视口 <1120px 时 `max-width` 大于可用宽度会被忽略，元素仍 100% 贴边不溢出；
  DefaultLayout 的 `.rule-line` / `.canvas-fill` 用 `max(0px, …)` 兜负值 + <1280px 隐藏，无不对称白带。

### 排查方法（可复用）
1. `grep -ho "\.shell{[^}]*}" dist/assets/*.css` + `grep -ho "\-\-shell-max:[^;}]*"` —— **直接从 dist 产物取现值**，
   比猜快得多；再把 dist 与 `src/styles/*.css` 的变量做 `comm` 双向差集，一次锁定差异集合。
2. 顺带确认：`vite preview` **自动继承 `server.proxy`**（Vite `resolvePreviewOptions` 里
   `proxy: preview?.proxy ?? server.proxy`），所以 `/api` 两边行为本来就一致，**无需给 vite.config 加 preview.proxy**。
3. 用户选择本轮**只改 CSS 不重建** → `dist` 仍落后源码 12 天（10/04 留言页改版等均不在其中），
   **要让「其他全部一样」落地，只需再跑一次 `npm run build`**（dev 已回到 preview 的容器值）。

### 工具坑（已在 scripts/shot.mjs 内修掉）

## 22:40 评估：访问埋点/省份分布能否投产（结论：不能直接用）

用户问「准不准、能不能投产」。逐项核对代码后列出 5 个问题（**尚未修，仅评估**）：

1. **口径错（硬伤）**：`todayVisitTotal` 叫「今日访问」实为**接口请求数**；首页一次打开并发调 4 个
   `/portal` GET（`HomeView.vue` 109-112：getArticleList/getCategories/getTags/getSiteStats）→ **一次浏览写 4 行**。
   数字向人解释不通，属「错」而非「不精」。
2. **可伪造 / 可灌水**：`IpUtils.getClientIp` 无条件采信 `X-Forwarded-For` 首值，**无可信代理校验** →
   任意客户端伪造 IP 即伪造省份；且埋点无去重、无限流、无采样，爬虫/刷新可线性灌水。
3. **省份解析依赖第三方免费接口**：`whois.pconline.com.cn`（GBK、明文 HTTP、无 SLA）；
   `ProvinceResolver` 用 `cache.computeIfAbsent(ip, this::queryRemote)` —— **失败结果也被永久缓存**，
   接口抖动一次该 IP 后续永远是「未知」；且是单机内存缓存，重启即失效（多实例各算各的）。
4. **`ProvinceResolver.isLocal()` 死代码**：第 74 行 `ip.startsWith("172.")` 已 return true，
   下面 77-85 行想精修 172.16-31 的逻辑**永不可达** → 公网 172.x 被误判「本地」。
   （同类写法在 `IpUtils.getLocation` 里是**正确的**，只有 ProvinceResolver 写错。）
5. **容量只增不减**：`t_visit_log` 无归档、无 TTL、无清理任务。索引没问题——
   `idx_visit_time(create_time)` + `idx_visit_province(province, create_time)`，今日查询走索引，
   不随表增大而变慢；问题只在磁盘/备份膨胀（按 4 行/页估，10 万 PV/月 ≈ 40 万行/月）。
   另：`Executors.newSingleThreadExecutor` 是**无界队列**，DB 持续变慢时内存无上限。

**修复建议（免费 / 简单两案，待用户确认后再动手）**：
- 免费案：`ip2region` 离线 xdb 替掉第三方接口（本地微秒级、无 SLA、无缓存失效问题）
- 简单案：埋点加 `visitor_key` 列复用 `VisitorKey.of(request)`，今日访问改 `COUNT(DISTINCT visitor_key)`；
  XFF 加可信代理白名单；加 `@Scheduled` 清理 90 天前日志；执行器换有界队列
- 结论：**毕业设计演示 + 个人博客低流量自用可以，但文档需诚实标注口径**；对外报数则必须先修 1、2
